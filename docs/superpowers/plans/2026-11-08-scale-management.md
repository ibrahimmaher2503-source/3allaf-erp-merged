# خطة إدارة الميزان وربطه بالأصناف والأسعار

> For agentic workers: use `executing-plans` task by task after owner approval. This document is a proposal, not execution authorization. All checkboxes are pending.

**Goal:** إرسال الأصناف والأسعار إلى الميزان، تعيين أزراره، إدارة طباعة ملصقاته، وإظهار الصنف والوزن والسعر الواردين منه داخل النظام.

**Architecture:** امتداد داخل Laravel modular monolith بواجهة Blade/Livewire/Flux. يعاد استخدام مصدر التسعير الحالي. يتصل التطبيق بالميزان مباشرة عندما يكون الخادم على نفس الشبكة؛ عند الاستضافة الخارجية يلزم موصل محلي مقيد للتعامل مع العتاد، وليس تطبيق أعمال أو قاعدة بيانات مستقلة.

**Tech Stack:** PHP/Laravel المثبتان، Livewire وFlux المثبتان، MySQL/MariaDB، وبروتوكول الشركة المصنّعة بعد إثباته. لا تعتمد مكتبة أو SDK أو خدمة Windows قبل مراجعة توافقها وترخيصها.

**Spec:** طلب المالك في هذه المحادثة بتاريخ 2026-11-08؛ هذه الوثيقة تجمع التصميم المقترح وخطة التنفيذ للمراجعة قبل العمل.

**توجيه المالك أثناء التنفيذ:** تعريف الجهاز وإرسال الأسعار وتعيين الأزرار والقوالب واستقبال النتائج كلها من ERP. برنامج MScale وملفات الاستيراد اليدوي خارجة عن مسار التشغيل والقبول. إذا احتاج الخادم البعيد إلى موصل محلي، يعمل في الخلفية وتبقى الأوامر والنتائج في ERP. الميزان الحالي فارغ حسب إفادة المالك، ولذلك تم تجاوز سحب نسخة الأصناف كشرط لتجربة صنف واحد على هذا الجهاز تحديدًا.

## النطاق وحالة الأدلة

- المؤكد من الفحص السابق: الجهاز على Ethernet 2 أعلن IP `192.168.0.150` وMAC `00:23:f0:1b:15:77`، والمنفذ `33581` قبل اتصال TCP بعد إضافة `192.168.0.151/24` للكمبيوتر. لم تصل بيانات تلقائية خلال انتظار خمس ثوانٍ. حدث timeout في محاولة قصيرة ثم نجحت محاولات تالية.
- غير المؤكد: الموديل والـfirmware، بروتوكول رفع PLU وقراءة البيانات، دعم تعديل الأزرار والقوالب عن بعد، وحدود الأصناف والخطوط العربية والباركود، وهل يعرض الجهاز الوزن الحي أم يصدّر معاملات مطبوعة فقط.
- تشابه أرقام المنافذ مع دليل TM-A لا يثبت الهوية ولا يبرر إرسال أوامر ذلك الموديل.
- الكود السابق في `feature/device-settings` مجرد إعداد اتصال أولي، غير مرحّل وغير مقبول بصريًا. لا يمثل تنفيذ هذه الخطة. يراجع قبل إعادة استخدامه، خصوصًا افتراض ميزان واحد للشركة واختبار الاتصال من الخادم.
- هذه جلسة تخطيط فقط: لا أوامر كتابة للميزان، ولا ترحيل أو تعديل إضافي لكود التطبيق، ولا commit/push/deploy.

## تجربة المستخدم المقترحة

1. من «الأجهزة والطباعة» يفتح المستخدم جهاز ميزان محددًا، مرتبطًا بمنفذ البيع والكمبيوتر/الموصل الذي يصل إليه.
2. تبويب «الأصناف والأسعار»: اختيار أصناف موجودة، ربط كل صنف ووحدة بيع برقم PLU في الميزان، ثم معاينة وإرسال.
3. عند تغيير السعر يظهر «يحتاج تحديثًا» وزر «إرسال للميزان» في قائمة أصناف الميزان؛ زر الصنف أو شاشة التسعير يفتح نفس المعاينة مع الأجهزة المتأثرة. لا يحدث إرسال تلقائي بمجرد حفظ المنتج.
4. تبويب «الأزرار»: شبكة تحاكي عدد وصفوف وأماكن الأزرار الفعلية، تعرض رقم الزر والصنف المرتبط، ثم معاينة وإرسال التعيينات.
5. تبويب «طباعة الميزان»: قالب الملصق ومقاسه وحقوله المسموح بها ومعاينة، ثم إرسال القالب وطباعة عينة فعلية عند الطلب.
6. تبويب «قراءات الميزان»: الصنف وPLU والوزن الصافي ووحدته وسعر الوحدة والإجمالي، مع حالة الثبات ووقت آخر قراءة ومصدرها. يعرض «غير مدعوم» للقدرة غير الموجودة، و«قراءة قديمة» بدل إبقاء وزن قديم ظاهرًا كأنه حي.
7. تبويب «سجل الإرسال»: من أرسل، وما الذي أرسل، والسعر السابق والجديد، والأصناف الناجحة والفاشلة، ونتيجة التحقق.

## قرارات التصميم المقترحة

### مصدر السعر ووحدة البيع

- النظام هو مصدر الأصناف والأسعار المعتمد. يعاد استخدام `EffectivePriceResolver::resolve` و`PriceListResolver` حسب منفذ البيع ووحدة الصنف، دون إنشاء حاسبة أسعار ثانية.
- لا يكفي نسخ `products.sale_price`: توجد أسعار منفذ وأسعار قوائم وتجاوزات ووحدات. الميزان العام لا يستقبل تلقائيًا أسعار عميل خاص أو خصومات سلة.
- يختار ملف الميزان سياق منفذ البيع؛ يرسل السعر الساري وقت المعاينة، بعد التحقق مجددًا عند التنفيذ. السعر المستقبلي يبقى مؤجلاً إلى تاريخ سريانه.
- حفظ ربط صريح بين وحدة النظام ووحدة التسعير في الميزان: كجم/جرام/قطعة وفق دعم الجهاز. تستخدم أعداد عشرية دقيقة وتحويلات الوحدات الموجودة. يمنع الإرسال عند غموض هل السعر للكجم أم للكيس أو عند تجاوز الدقة/السعة.
- يوضح شكل السعر المطلوب على الملصق ومعاملة الضريبة قبل التنفيذ. أي اختلاف مع حسابات النظام يوقف الإرسال ولا يعالج بتقريب صامت.

### الاتصال

- الخيار المفضل: بروتوكول/SDK رسمي يثبت القراءة والكتابة والإقرار. الاتصال المباشر مناسب فقط لخادم يستطيع الوصول إلى شبكة الميزان.
- إذا كان ERP مستضافًا خارجيًا: موصل محلي على كمبيوتر المحل يسحب مهام مصادقًا عليها عبر HTTPS ويرجع نتائجها، مع تقييد الأجهزة والأوامر. لا يفتح منفذ الميزان للإنترنت ولا يعتمد المتصفح على TCP خام.
- عند غياب بروتوكول أو SDK قابل للتحقق، تبقى عمليات الجهاز معلقة. قبول الميزة يتطلب تنفيذها والتحقق من نتيجتها من ERP.
- لا يبدأ بناء الموصل أو اختيار لغته إلا بعد معرفة متطلبات SDK وبيئة الاستضافة. لا تبنى منصة أجهزة عامة؛ ينفذ موصل الجهاز المثبت فقط.

### الاستقبال

- تفرق الواجهة بين قراءة حية، سجل عملية طباعة/بيع، وباركود ملصق ممسوح. لا تستخدم بيانات نوع مكان الآخر.
- إذا أتاح البروتوكول الوزن فقط، يعرض الصنف والسعر كغير متاحين؛ لا يستنتجان من آخر صنف أرسله النظام.
- إذا أتاح سجلات فقط، تستورد كقراءات/عمليات واردة مع معرف الجهاز والسجل لمنع التكرار، دون تسجيل مبيعات أو خصم مخزون تلقائي.
- يمكن دعم باركود الوزن/السعر كمسار بديل بعد تثبيت مخططه: بادئة، PLU، خانات الوزن أو المبلغ، الكسور، checksum. لا يفترض أن أي EAN-13 يحتوي وزنًا.

## نموذج البيانات المقترح

التصميم النهائي يتبع قدرات الجهاز بعد المرحلة الأولى؛ الأسماء التالية حدود واضحة وليست تفويضًا لإنشاء جداول غير لازمة.

| الجدول | الوظيفة والقيود |
|---|---|
| `scale_configurations` | أجهزة متعددة للشركة/منفذ البيع؛ اسم، موديل/firmware مثبتان، عنوان/منفذ، سياق التسعير، الموصل، قدرات مدعومة، حالة. تراجع migration الأولية غير المنفذة بدل إضافة افتراض ميزان واحد للشركة. |
| `scale_product_mappings` | جهاز + صنف + ProductUnit + PLU، اسم مختصر خاص بالميزان دون تغيير اسم المنتج الأصلي، حالة. تفرد PLU داخل الجهاز. |
| `scale_key_assignments` | جهاز + صفحة/طبقة + رقم زر + ربط PLU؛ تفرد موقع الزر ومنع الإرسال لصنف لم يثبت تحميله. |
| `scale_label_templates` | نسخة قالب خاص بالميزان وحقوله وأبعاده وإعدادات الباركود المتوافقة. منفصل عن HTML/Blade لطباعة المتصفح. |
| `scale_sync_batches` / `scale_sync_items` | snapshot الحمولة وإصدارها/hash، معرف طلب فريد، حالة كل عنصر، acknowledgment/readback، أخطاء وإعادة محاولة وتوقيت وهوية المستخدم. |
| `scale_readings` | عند الحاجة للتاريخ فقط: بيانات واردة محدودة الاحتفاظ، المصدر والوحدة والثبات والوقت ومعرف منع التكرار. القراءة الحية وحدها لا تتطلب تخزين كل عينة. |

جميع العلاقات scoped بالشركة والمنفذ؛ تمنع المراجع إلى أصناف/وحدات من شركة أخرى. الأسرار لا تدخل JSON الواجهة أو السجلات. لا تحذف عملية تعطيل الجهاز تاريخ إرسال سابقًا.

## خطة التنفيذ بالترتيب

### 1. إثبات قدرات الجهاز — بوابة إلزامية

- [ ] تحديد الموديل والـfirmware من برنامج الشركة أو بيانات تعريف موثقة، وجمع دليل البروتوكول/SDK وعينة ملفات الاستيراد والأزرار والقوالب إن وجدت.
- [ ] استخراج نسخة من الأصناف والأزرار والقالب الحاليين قبل أول كتابة، وتوثيق الاسترجاع دون factory reset.
- [ ] توثيق جدول دعم: قراءة تعريف، تحميل صنف، تحديث سعر، readback/ACK، أزرار، قالب، وزن حي، صنف حالي، معاملات مطبوعة.
- [ ] تجربة صنف اختبار غير مستخدم، ثم تعديل سعره واسترجاعه؛ لا تستخدم أوامر عشوائية أو أوامر المعايرة.
- [ ] تثبيت وحدات القياس والكسور وترميز العربية والسعة وأرقام PLU والأزرار وأبعاد الملصق.

**القبول:** دليل قابل لإعادة التجربة لكل قدرة، أو تحديد صريح أنها غير مدعومة. إذا تعذر الوصول لبروتوكول رسمي، يقدم مسار الملفات كحل محدود قبل الاستثمار في UI يعد بقدرات غير مثبتة.

### 2. تعريف الأجهزة والاتصال

**المسارات:** مراجعة `app/Modules/Platform/Models/ScaleConfiguration.php` وmigration `2026_11_08_160521_create_scale_configurations_table.php`؛ واجهة مستقلة `resources/views/platform/admin/scales.blade.php` مرتبطة بصفحة الطابعات الحالية؛ ربط في `routes/platform.php`.

- [ ] تحويل تعريف الشركة الواحد إلى أجهزة مرتبطة بمنفذ البيع وسياق التسعير والموصل الفعلي عند الحاجة.
- [ ] فصل «الإعداد محفوظ» عن «متصل» وعن «البروتوكول متوافق»، وإلغاء النتيجة السابقة عند تغيير العنوان/المنفذ.
- [ ] تنفيذ اتصال بمهلة محدودة، قفل جلسة لكل جهاز، heartbeat عند استخدام موصل، وأخطاء عربية مفهومة.
- [ ] تطبيق صلاحيات الخادم: عرض، إدارة جهاز، إرسال، أزرار، قالب، قراءة؛ توثيق مصفوفة المنح دون منحها للأدوار تلقائيًا.

**القبول:** حفظ/إعادة فتح/تعطيل، عنوان خاطئ وجهاز مغلق، منع مستخدم أو منفذ غير مخول، وعدم نجاح اختبار من خادم لا يصل للشبكة.

### 3. ربط الأصناف وإعداد الأسعار

**المسارات:** نماذج الربط الجديدة داخل `app/Modules/Platform/Models/`، ومكوّن شاشة الميزان. قراءة `app/Modules/Catalog/Models/Product.php` و`ProductUnit.php` وخدمات `app/Modules/Pricing/Services/` دون تغيير معادلاتها.

- [ ] قائمة server-side للأصناف القابلة للإرسال، اختيار جماعي محدود، وإسناد PLU يدوي/اقتراح متحقق من عدم التكرار.
- [ ] معاينة اسم الميزان والباركود والوحدة وسعرها ومصدر السعر وسريانه، ورفض الاسم/الباركود غير القابلين للتمثيل بدل اقتطاع صامت.
- [ ] إنشاء snapshot محدد للجهاز والسعر والوحدة والحقول المدعومة، بلا اعتماد على بيانات Livewire يرسلها العميل باعتبارها السعر الصحيح.

**القبول:** صنف وزني وآخر بالقطعة، تحويل وحدات، سعر مفقود/مستقبلي، PLU مكرر، صنف معطل، شركة أخرى، وأسماء عربية وحدود كسور الجهاز.

### 4. الإرسال وتحديث السعر

**المسارات المقترحة:** `app/Modules/Platform/Actions/PrepareScaleSync.php`، `Jobs/SendScaleSync.php`، `Services/ScaleProtocol.php` مع تنفيذ واحد للبروتوكول المثبت، ونماذج الدفعات. دمج زر من شاشة الصنف/التسعير بعد تحديد ملفاتها ومراجعة Core.

- [ ] إضافة «إرسال المحدد» و«إرسال المتغيرات». يقارن النظام الحمولة المطلوبة بآخر حمولة مؤكدة، بما يغطي تغير القائمة والسريان والتجاوزات، لا مجرد وقت تعديل المنتج.
- [ ] دورة حالات: جاهز، في الانتظار، جارٍ الإرسال، مؤكد، فشل، نتيجة غير معروفة. الإرسال على socket وحده ليس تأكيدًا.
- [ ] تسلسل المهام لكل جهاز، منع الضغط المكرر، وإعادة محاولة العناصر التي تسمح دلالة البروتوكول بإعادتها. عند فقد الرد بعد الكتابة ينفذ readback أو يطلب تحققًا بدل إرسال أعمى.
- [ ] إذا تغير السعر بعد تجهيز الدفعة وقبل إرسالها تمنع الحمولة القديمة وتطلب إعادة التجهيز؛ إذا تغير أثناء التنفيذ يبقى الجهاز «يحتاج تحديثًا» بعد إنهاء القديم.
- [ ] سجل تدقيق لطلب الإرسال ونتيجته وتفاصيل الفشل، واسترجاع إعدادات سابقة فقط بعد معاينة أثر إعادة السعر القديم.

**القبول:** تأكيد السعر على شاشة الميزان وملصقه، انقطاع في منتصف دفعة، نجاح جزئي، فقد ACK، ضغط مزدوج، تغير السعر أثناء الانتظار، وانتهاء مهلة. يمنع بقاء مؤشر «محدث» إذا وصل إصدار قديم.

### 5. برمجة الأزرار

- [ ] تمثيل الأزرار والطبقات من ملف قدرات الجهاز، مع إسناد صنف والبحث والتبديل ومسح التعيين بمعاينة أثره.
- [ ] إرسال الفروقات المدعومة والتحقق، وتصدير/حفظ نسخة التخطيط السابقة قبل استبدالها.
- [ ] عدم عرض تحكم عن بعد إن كان الجهاز يدعم ملف مفاتيح فقط؛ يقدم ملفًا متوافقًا وتعليمات استيراده وحالة التحقق.

**القبول:** الضغط على عدة أزرار فعلية يستدعي الأصناف الصحيحة، بما فيها الطبقات والحواف؛ لا يرسل زر قبل تحميل PLU المطلوب.

### 6. قالب طباعة الميزان

- [ ] دعم حقول الجهاز الفعلية: اسم المتجر/الصنف، PLU/باركود، الوزن، سعر الوحدة، الإجمالي والتاريخ وما يتيحه الجهاز. قالب browser الحالي ليس صيغة صالحة للميزان تلقائيًا.
- [ ] أول إصدار يحرر المقاسات والحقول وإعداداتها التي يدعمها SDK؛ لا يبنى محرر تصميم حر ما لم يدعمه الجهاز وتثبت الحاجة.
- [ ] تحقق من الدقة والطول والترميز والمقاس والباركود قبل الرفع؛ حفظ نسخة ومقارنة وإرسال ثم عينة مطبوعة.

**القبول:** ملصق عربي واضح بلا قص، وزن وسعر وإجمالي صحيحون، باركود مقروء بالقارئ الفعلي، وعودة ناجحة للقالب السابق.

### 7. استقبال الصنف والوزن والسعر

- [ ] تنفيذ reader للبروتوكول المثبت فقط؛ تحقق من الإطار/checksum والوحدة والثبات والوزن السلبي/الزائد والطابع الزمني.
- [ ] شاشة قراءات مستقلة تحمل هوية الجهاز، وتمنع إسناد PLU غير معروف إلى صنف افتراضي؛ تظهر قراءة متوقفة/قديمة بوضوح.
- [ ] تثبيت معنى السعر الوارد: سعر الوحدة أم الإجمالي، وما إذا كان شامل الضريبة، مع عرض اختلافه عن سعر النظام دون تعديل أي منهما تلقائيًا.
- [ ] قياس المقارنة بصفر ووزنين معلومين وبوزن غير ثابت، واختبار إعادة الاتصال وتكرار السجل واختلاف الوحدة.

**القبول:** القيم تطابق شاشة الميزان ضمن دقة الجهاز الموثقة، وتختفي صفة «حي» فور انتهاء مهلة القراءة. إذا كان الجهاز لا يتيح الصنف/السعر مباشرة، يسجل القيد ويقدم بديل باركود/سجل معاملات بموافقة المالك دون ادعاء التكافؤ.

### 8. الربط الاختياري بفاتورة البيع — خارج التنفيذ حتى موافقة Core

**CORE CHANGE REQUIRED** إذا طلب اعتماد القراءة في POS/المبيعات أو تفسير باركود الوزن هناك أو تغيير الصلاحيات الأساسية.

- القديم: كمية وسعر مصدرهما مسار المبيعات والتسعير الحالي. الجديد المقترح: «استخدام قراءة الميزان» يجهز سطرًا للمراجعة، ثم يمر بخدمات التحقق والتسعير الحالية.
- يجب أن يقرر المالك قبول السعر الوارد أو إعادة تسعيره، والتعامل مع اختلاف السعر والضريبة، وهل السجل المستورد مجرد وزن أم بيع نهائي.
- تراجع الوحدات والمخزون والإرجاع والخصم والصلاحيات والتدقيق ومنع تكرار العملية. لا يخصم مخزون ولا تسجل دفعة عند استقبال قراءة فقط.
- توثق موافقة دقيقة للسلوك القديم والجديد والوحدات المتأثرة ونطاق regression وأثر migrations والرجوع. هذه الخطة ليست تلك الموافقة.

## التحقق والتسليم والرجوع

- تبدأ كل مرحلة بدليل نجاحها على الجهاز الفعلي ونسخة إعداداته. PHP lint وPint وBlade compilation وlocale/diff checks بحسب الملفات المتغيرة؛ لا تكرر checks ناجحة دون تغيير.
- الاختبارات الآلية غير مصرح بها حاليًا لهذه المهمة. الخطة تقترح لاحقًا نطاقًا مسمى: تحويل السعر والوحدة، ترميز البروتوكول، ACK/timeout/retry، العزل والصلاحيات، ورفض القراءة القديمة. يلزم تفويض هذا النطاق قبل تشغيله، ولا تعتبره مكتملًا الآن.
- تفحص الواجهة عربي RTL وإنجليزي LTR ومقاسات مناسبة، وحالات التحميل/الفراغ/الخطأ/النجاح/التعطيل/رفض الصلاحية/التحقق/تأكيد الإرسال/تغييرات غير محفوظة.
- migrations إضافية متوافقة، مراجعتها قبل التنفيذ، واستخدام MariaDB محلية محددة بالاسم عند الفحص. لا SQLite ولا migration شامل على قاعدة غير متحققة.
- حد التسليم الأول: تعريف الجهاز + أصناف/أسعار + تحديث موثوق مع readback/إقرار. يليه الأزرار والطباعة ثم الاستقبال. الهدف النهائي لا يعد مكتملًا قبل قبول جميع القدرات المطلوبة أو قرار صريح بالبديل عند قصور العتاد.
- الرجوع: إيقاف عامل/موصل الإرسال، منع مهام جديدة، حفظ التاريخ، استعادة إعدادات الميزان من النسخة الموثقة. لا يكفي rollback للكود لاسترجاع أسعار كتبت إلى جهاز خارجي.
- لا دمج لمسار الإنتاج قبل مراجعة Core والمigrations والاختبارات المفروضة للمسار. لا نشر أو فتح منافذ عامة ضمن الموافقة على الخطة.

## ما يلزم حسمه في مرحلة الإثبات

هوية الجهاز وfirmware، توفر SDK، موضع خادم ERP بالنسبة للمحل، وحدة تسعير الأصناف وسياسة الضريبة، عدد الميزان/المنافذ، شكل الملصق والمفاتيح، وهل المطلوب استقبال حي أم عمليات مطبوعة أم إدخال تلقائي للفواتير. لا يمنع ذلك مراجعة التصميم الآن، لكنه يمنع الوعد ببروتوكول أو قدرة غير مثبتة.
